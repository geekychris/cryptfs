# CryptoFS Fuzz Harnesses

Two libFuzzer targets exercise the crypto path shared with
[`tests/crypto_verify`](../crypto_verify/), via the primitives in
[`tests/crypto_verify/cryptofs_crypto.h`](../crypto_verify/cryptofs_crypto.h).

## What's being fuzzed, and what isn't

The kernel's real encryption code lives in `kernel/crypto.c` and depends on
the in-kernel Crypto API (`crypto_aead`, `crypto_shash`) -- it cannot be
linked into a userspace fuzz binary. Instead, these harnesses fuzz the
userspace OpenSSL reimplementation in `cryptofs_crypto.h`, which
`tests/crypto_verify/crypto_verify.c` already verifies is byte-compatible
with the kernel (same constants, same on-disk header layout, same
AES-256-GCM + HMAC-SHA256 scheme, 20/20 tests passing). A bug found here is
a bug in a parallel, verified-equivalent implementation of the kernel
logic -- not a bug in `kernel/crypto.c` itself.

## Targets

### `fuzz_extent_crypto.c`

Feeds fuzzer-controlled key/nonce/tag/ciphertext straight into
`decrypt_extent()` (it must return 0 or -1, never crash), then round-trips
`encrypt_extent() -> decrypt_extent()` and asserts the plaintext is
unchanged. Also exercises `gcm_wrap()`/`gcm_unwrap()` (used for FEK
wrapping) at lengths below, at, and above `CRYPTOFS_KEY_SIZE` (32).

### `fuzz_parse_file.c`

Treats the whole fuzzer input as an adversarial lower-file byte buffer and
calls `cryptofs_parse_and_decrypt_file()`, which mirrors the kernel VFS
read path (`kernel/file.c` `cryptofs_read_iter`, `kernel/inode.c`'s
extent-count-from-size math): parse header -> unwrap FEK -> compute
`num_extents` from the header's `file_size` with overflow-checked
arithmetic -> decrypt each extent -> truncate the last one to `file_size`.
It must return a clean error code on every path and never read past
`buf_len`, however adversarial the header or `file_size` is -- including
values near `UINT64_MAX` and non-extent-aligned sizes.

#### Why the corpus is pre-seeded with valid FEKs

`cryptofs_parse_and_decrypt_file()` GCM-authenticates the wrapped FEK
before doing anything else. A 128-bit auth tag cannot be forged by random
mutation, so an unseeded fuzzer would spend 100% of its time dying at that
one check and would never reach the `file_size`/extent-count math this
harness is actually meant to cover.

To get past that, `fuzz_parse_file.c` uses a **fixed, harness-only,
all-zero master key** (`FIXED_MASTER_KEY`) -- `cryptofs_parse_and_decrypt_file()`
takes the master key as a plain argument (the kernel instead resolves it
from an in-kernel key table), so the harness has to supply one. The seed
corpus under `corpus/fuzz_parse_file/` was generated by
[`corpus/gen_seeds.c`](corpus/gen_seeds.c) against that same key, so the
seeds' FEKs unwrap successfully and libFuzzer's coverage-guided mutation
can spend its time on the size/extent math instead of the auth check.

This means `fuzz_parse_file` cannot discover anything about GCM itself
(that's `fuzz_extent_crypto`'s job) -- it is scoped to the file-structure
parsing logic that sits in front of the per-extent decryption.

## Running locally

Requires `clang` (for `-fsanitize=fuzzer`) and `libssl-dev`.

```sh
make fuzz-build                    # from the repo root, or `make build` in this dir
./fuzz_extent_crypto -max_total_time=300 corpus/fuzz_extent_crypto/
./fuzz_parse_file    -max_total_time=300 corpus/fuzz_parse_file/
```

`make fuzz-replay` (or `make replay` in this directory) runs both targets
with `-runs=0` over the checked-in corpus only -- no new mutation, just a
fast regression check that exits non-zero if any checked-in seed now
crashes or trips ASan/UBSan.

## CI

[`.github/workflows/fuzz.yml`](../../.github/workflows/fuzz.yml) runs on a
daily schedule and via manual `workflow_dispatch` (with a
`seconds_per_target` input, default 300s). It builds both harnesses, runs
the regression replay, then fuzzes each target for the bounded time,
uploading any `crash-*`/`oom-*`/`timeout-*`/`leak-*` artifact on failure.
It is intentionally *not* wired into the PR path: it needs clang and runs
for minutes, so it stays schedule/manual-only and can't block or slow any
pull request.

## Adding a regression seed from a crash

If a run finds a crash, libFuzzer writes a `crash-<hash>` file (or
downloads it as a CI artifact). To turn it into a permanent regression
test:

1. Root-cause and fix the bug in `cryptofs_crypto.h` (and, if it's a real
   logic bug rather than a quirk of the userspace reimplementation,
   file a matching fix in `kernel/crypto.c`).
2. Copy the crashing input into `corpus/<target>/` with a descriptive name,
   e.g. `corpus/fuzz_parse_file/regression_<short-description>`.
3. Run `make fuzz-replay` to confirm it now passes.
4. Commit the fix and the new seed together.
